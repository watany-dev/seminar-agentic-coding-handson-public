Step2 テスト、リント

目次に戻る

目的

/quality-check の実行結果を読み、何が成功して何が失敗したのかを根拠付きで説明できるようにします。このステップでは直しません。

所要時間の目安

10分（16:55〜17:05）：解説2分、結果の読み取り6分、振り返り2分。

手順

未完成　ここに入る内容は準備中です（WS p.64〜66、p.68〜70、ハーネス p.40）

1. 3つのチェックの役割

  • テスト：決めた入力・操作に対して、期待どおりに動くかを確かめる。
  • リント：コードを動かさずに、ルール違反や問題の兆候を調べる。
  • 型チェック：型の食い違いがないかを調べる。

どれか一つが成功しても、ほかの観点の問題は見つかりません。

2. 結果を読む

先ほどの /quality-check の報告から、次の問いに答えます。

チェック 読み取ること
テスト 全部で何件あり、何件が失敗したか。失敗したテストの名前は何か
リント どのファイルの、何が指摘されたか
型チェック 成功したか

失敗したテストについて、Claude Codeに詳しく聞きます。

失敗したテストについて、テスト名、期待した値、実際の値を教えてください。
原因の調査と修正はまだしないでください。

報告が実際のログと合っているか、ターミナルの出力と見比べます。

3. 画面で症状を確かめる

テストの失敗が、アプリの動きとしてはどう見えるかを確かめます。Step1で開いた画面で、「少人数ワークショップ」が残席1の初期状態であることを確認してください。状態が違う場合は、開発サーバのターミナルで Ctrl+C を押して停止し、教材リポジトリのルートで npm run dev を実行して再起動し、画面を再読み込みします。

残席1から、次を試してください。2回の申込は、初期申込者とも重複しない別々のメールアドレスで行います。

  1. 「少人数ワークショップ」（定員3名、残り1席）に申し込む。
  2. 別のメールアドレスで、もう一度同じセミナーに申し込む。

何が起きたでしょうか。README.md の「仕様」の「申込」と見比べ、失敗したテストと同じ問題かどうかを考えます。

4. 「成功」の中身も見る

  • テストは失敗した1件以外は成功しています。成功した件数も結果の一部です。
  • 型チェックは成功しましたが、いま画面で見た問題は見つけていません。

完了条件： 3つのチェックそれぞれの結果を言える。失敗したテストの名前と、画面で見た症状を説明できる。

Step2 危険操作の抑止（紹介）

目次に戻る

目的

エージェントへ作業を任せる範囲と、人の承認・実行環境で守る境界を区別します。

所要時間の目安

3分（17:05〜17:08）。講師の紹介を聞くパートです。手元での操作はありません。

見るポイント

危険操作の抑止については、当日スライドを参照してください。

1. 指示と強制力は別のもの

CLAUDE.md やSkillに「危険な操作をしない」と書くことは作業方針の共有です。それだけで操作が技術的に禁止されるわけではありません。実行権限、承認、環境の分離、復旧可能な変更管理も組み合わせます。

2. 承認を求められたら確認すること

講師が示す権限確認の画面を、次の観点で見てください。

  • 対象のパス・リポジトリ・接続先はどこか。
  • ファイルの削除、大規模な上書き、履歴の書き換え、外部への送信を含まないか。
  • 本番環境・秘密情報にアクセスできる状態になっていないか。
  • 必要以上に広い許可や、今後の操作の一括許可になっていないか。

3. 迷ったら止めて確認する

不明な操作は承認せず、目的と必要性、より狭い操作で代替できるかをエージェントに説明させます。権限確認が煩わしくても、一括で無効化しないでください。

確認ポイント： 「指示を書いたから安全」ではなく、実行できる範囲と検証の仕組みも必要だと説明できること。

Step2 脆弱性スキャン

目次に戻る

目的

依存パッケージの既知の脆弱性をスキャンし、指摘を読み、優先順位を付け、1件を修正して再スキャンするまでを体験します。

所要時間の目安

12分（17:08〜17:20）：スキャン3分、結果の読み取り3分、修正4分、再スキャンと確認2分。

手順

1. スキャンさせる

Claude Codeへ入力します。

npm audit を実行して、指摘をパッケージごとの表にしてください。
列は、深刻度、実行時の依存か開発時だけの依存か、
修正方法（npm audit fix で直るか、メジャー更新が必要か）です。
まだ何も変更しないでください。

npm audit の終了コードが0以外でも、脆弱性の監査レポートが取得できていれば「指摘あり」と読み取れます。終了コードだけでは判断せず、出力を確認してください。

403・通信エラー・認証エラーで監査レポート自体を取得できない場合は、監査未完了です。指摘件数は不明であり、0件でも「指摘あり」でもありません。出力ログを保存して講師へ連絡し、監査結果に基づく更新・件数比較・指摘の消失確認は進めず、講師の案内を待ちます。再スキャンで取得できない場合も同じ扱いとし、消失確認は未完了と記録してください。

2. 結果を読む

監査レポートを取得できた場合に、その結果を読みます。以下は配布時の例で、指摘は大きく2つの系統に分かれます。実際に取得した結果を優先し、validator の指摘がない場合や修正方法が異なる場合は、講師へ確認してください。

  • validator
  • vitest とその配下（vite、esbuild、tinypool など）

次の観点で、どちらを先に対応するかを考えます。

観点 確認すること
深刻度 critical／high／moderate／low。これだけで機械的には決めない
利用経路 アプリの実行時に使うか、開発時だけか。外部からの入力が届くか
修正のしやすさ 互換範囲の更新で直るか、破壊的変更を伴うメジャー更新が必要か

手がかり：validator は申込フォームのメールアドレス検証（src/rules.ts）で使われています。vitest はテストを実行するときだけ使います。分からなければClaude Codeに「validator はこのアプリのどこで使われていますか」と聞いてください。

3. 1件だけ修正させる

今回は、実行時に使われ、互換範囲で直せる validator を修正します。

validator だけを、package.jsonの指定範囲内で修正版に更新してください。
npm audit fix --force は使わず、他のパッケージは変更しないでください。

4. 再スキャンして確かめる

  1. VS Code左の「ソース管理」で、新たに変更されたのが package-lock.json だけであることを確認します。

  2. 再スキャンさせます。

    npm audit を再実行して、修正前との違いを教えてください。

    件数だけでなく、validator の指摘が消えたことを確認します。

  3. 更新でアプリが壊れていないかを確かめます。

    /quality-check

    結果が前のステップと同じ（失敗するテストとリントの指摘が同じ）なら、今回の3チェック（テスト・リント・型チェック）では新しい失敗は見つからなかったと判断します。未検証の動作は残るため、アプリ全体に問題がないという意味ではありません。

5. 残った指摘を記録する

配布時の例では vitest 系の指摘が残り、解消にはメジャー更新が必要でした。テストの書き方や設定に影響する可能性があるため、今回は見送ります。実際に取得した再スキャンの一覧から「何が残っているか」「なぜ見送ったか」を記録し、一言で言えるようにしておきます。監査未完了の場合は、残存件数や消失を推測せず「指摘件数は不明・消失確認は未完了」と記録します。

指摘が0件になっても、それは「既知の脆弱性が登録されていない」という意味で、アプリ全体の安全を保証するものではありません。

完了条件： 監査レポートを取得でき、validator の指摘が再スキャンで消えている。残った指摘と、見送った理由を説明できる。監査未完了の場合は、この完了条件は未達としてログとともに講師へ報告する。

Step3 完成済み教材での品質検証

目次に戻る

目的

この教材アプリは、品質検証の練習用に意図的な不具合を含んでいます。「完成済み教材」は演習用に用意されたという意味で、不具合がないことを示す名称ではありません。

Step2で見つけた失敗を直し、直ったことを検証し、結果を報告するまでを一巡します。人が作業をずっと見張るのではなく、計画の承認と、検証結果の確認という節目で品質を確かめます。

所要時間の目安

20分（17:20〜17:40）：完了条件の確認3分、原因調査と修正計画7分、修正と再検証7分、結果共有3分。

手順

1. 現状と完了条件を確認する（3分）

いまの状態は次のとおりです。

  • テスト：1件失敗（画面では、定員を超えて申し込める）
  • リント：1件指摘
  • 型チェック：成功

この演習の完了条件

  • /quality-check の3つのチェックがすべて成功する。
  • テストとリントの設定には手を加えていない。
  • 画面で、定員を超える申込が断られる。

2. 原因を調べさせ、修正計画を承認する（7分）

失敗しているテストとリントの指摘について、原因を調べてください。
仕様はREADME.mdの「仕様」を正とします。
それぞれについて、原因、最小の修正案、変更するファイルを示し、
まだファイルは変更しないでください。

計画を次の観点で確認します。

  • 変更するのは src/ のファイルか。test/ や biome.json を変えようとしていないか。
  • 失敗したテストを解消するアプリ側の修正案（テスト自体は原則変更しない）は、README.md の仕様（定員に達したら受け付けない）と合っているか。
  • リントの修正案は、指摘を黙らせるだけの変更（変数名の先頭に _ を付けるなど）になっていないか。

納得できなければ、理由を伝えて案を出し直させます。

3. 修正させ、再検証する（7分）

計画を承認し、検証まで任せます。

その計画で修正し、/quality-check の手順で検証して結果を報告してください。

報告を受けたら、自分で確かめます。

  1. 報告の表で、3つのチェックがすべて成功しているか。テストの件数は修正前と同じか。
  2. 「ソース管理」で差分を開き、変更が計画どおりのファイル・行だけか。test/ に変更がないか。
  3. 画面で、「少人数ワークショップ」が残席1の初期状態であることを確認する。状態が違う場合は、開発サーバのターミナルで Ctrl+C を押して停止し、教材リポジトリのルートで npm run dev を実行して再起動し、画面を再読み込みする。残席1から、初期申込者とも重複しない別々のメールアドレスで2回申し込み、2回目が断られて残席が0のままか確かめる。

ここで確認できるのは、今回の3チェックと画面操作の範囲です。成功しても、未検証の動作は残り、アプリ全体に問題がないことを保証するものではありません。

3つのチェックが成功しない場合は、もう一度だけ原因を調べさせます。時間内に直らなければ、分かったところまでを次の報告に残します。

4. 結果を報告させ、共有する（3分）

今回の作業を次の形式でまとめてください。
- 直した問題と原因
- 変更したファイル
- 実行したコマンドと結果
- まだ残っている問題、今回のチェックでは確かめられていないこと

「まだ残っている問題」に、Step2の監査で実際に確認して見送った指摘（配布時の例では vitest 系）が入っているかを見ます。監査レポートを取得できなかった場合は「監査未完了・指摘件数は不明・消失確認は未完了」が入っているかを確認します。入っていなければ、エージェントの報告だけでは抜けが出るという例です。

最後に、確認できたことを一つ、残っていること・確かめられていないことを一つ、共有します。

完了条件： 3つのチェックが成功し、画面でも直ったことを確かめた。残っている問題を一つ挙げられる。
